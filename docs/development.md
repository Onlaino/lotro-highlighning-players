# Руководство разработчика Enemy Highlight

**Русский** | [English](development.en.md) · [К документации](README.md)

Этот документ описывает устройство плагина и безопасный цикл изменений.
Правила оформления вклада находятся в [CONTRIBUTING.md](../CONTRIBUTING.md),
планы функций — в [roadmap](roadmap.md).

## Требования к окружению

- установленный клиент LOTRO с поддержкой Lua-плагинов;
- каталог плагинов
  `Documents\The Lord of the Rings Online\Plugins`;
- Git и текстовый редактор;
- опционально — Lua-парсер или линтер для быстрой проверки синтаксиса.

Сборка и сторонние зависимости не требуются: исходники из
`HighlightPlayers/` загружаются клиентом напрямую. Окончательная проверка UI,
событий и PluginData возможна только внутри LOTRO.

## Жизненный цикл

`Main.lua` создаёт `App` и подключает обработчики загрузки и выгрузки. Во время
`App:Start()` компоненты создаются в следующей последовательности:

1. Storage загружает и нормализует PluginData.
2. Localization выбирает сохранённый или автоматический язык.
3. Labels и Relationships создают модель данных.
4. TargetTracker подписывается на смену цели.
5. Indicator и окна получают зависимости через конструкторы.
6. Launcher и Commands подключают пользовательские точки входа.

При `App:Stop()` подписки снимаются в обратном порядке, а Storage сохраняет
текущее состояние. Новый компонент должен иметь явный жизненный цикл и не
оставлять обработчики событий после выгрузки.

## PluginData и миграции

Данные сохраняются с ключом `HighlightPlayers` в
`Turbine.DataScope.Server`. Текущая версия схемы задаётся в
`Constants.DataVersion`.

При изменении сохраняемой структуры:

1. увеличьте `DataVersion`;
2. добавьте нормализацию старого значения в `Storage.lua`;
3. сохраните существующие записи и настройки, если они корректны;
4. сделайте преобразование идемпотентным;
5. проверьте пустые, частично повреждённые и предыдущие данные;
6. обновите пользовательское руководство и ручной сценарий.

Нельзя считать, что все поля или их типы корректны: PluginData может прийти из
старой версии либо быть изменён вручную. Не переименовывайте стабильный ID
метки при изменении её отображаемого имени.

Версия 4 добавляет позицию `noteWindow` и настройку
`settings.indicator.showNoteTooltip`. При загрузке версии 3 отсутствующие поля
получают безопасные значения по умолчанию, а записи игроков не изменяются.

Версия 5 добавляет `settings.language` со значениями `auto`, `en`, `fr`, `de`
или `ru`. Некорректное значение заменяется на `auto`; остальные данные не
изменяются.

## Локализация

Английский словарь является fallback. Все остальные словари обязаны содержать
тот же набор ключей и те же параметры шаблонов. Пользовательские строки нельзя
размещать непосредственно в UI или моделях: используйте
`HighlightPlayers.Localization.Get(key, values)`.

Окна подписываются через `Localization.AddListener` и снимают подписку в
`Stop`. При смене языка нельзя очищать введённые, но ещё не сохранённые данные.
Для пользовательского текста используются шрифты семейства Verdana с поддержкой
диакритических знаков и кириллицы. Названия меток не переводятся: это данные
пользователя, а не строки интерфейса.

## События и производительность

- Чтение цели выполняется по `TargetChanged`, а не на каждом кадре.
- Точное сопоставление имени использует таблицу по нормализованному ключу.
- Списки используют сессионные индексы и перестраиваются после мутаций.
- Закрытый или скрытый UI не должен получать клавиатурный фокус и перехватывать
  мышь.
- Индикатор всегда участвует в hit testing: hover и короткий клик доступны в
  любом режиме. `/eh move` разрешает drag, а `/eh lock` блокирует только
  изменение позиции.
- Фоновый таймер или `Update` требует отдельного обоснования и проверки в
  клиенте.

При изменении горячего пути проверьте быстрые смены целей и базы на 100, 500 и,
по возможности, 1000 записей.

## Локальный цикл разработки

1. Создайте ветку от актуальной `staging`.
2. Подключите рабочий каталог как `HighlightPlayers` в каталоге плагинов либо
   копируйте его туда после изменений.
3. Выполните `/plugins refresh` после изменения манифеста или состава модулей.
4. Перезагрузите плагин после изменений Lua.
5. Следите за Lua-ошибками и сообщениями с префиксом `[HighlightPlayers]`.
6. Выполните релевантные пункты
   [ручного сценария](manual-test.md).

Не используйте реальные пользовательские данные как тестовые без резервной
копии. Для проверки миграции сохраните отдельные образцы предыдущих версий вне
репозитория.

## Стиль изменений

- используйте пространство имён `HighlightPlayers`;
- объявляйте временные функции и значения через `local`;
- передавайте зависимости в конструктор вместо создания скрытых глобальных
  экземпляров;
- храните общие пределы и версии в `Constants.lua`;
- централизуйте пользовательские сообщения и не показывайте технический стек
  без контекста;
- обновляйте `__init__.lua`, если добавлен новый модуль;
- не добавляйте сгенерированные архивы и локальные task-файлы в Git.

Сохраняйте стиль соседнего кода: четыре пробела, один модуль на файл, ранний
выход для невалидного состояния и явные методы `Start`/`Stop` для подписок.

## Проверка изменений

Минимальная проверка любого изменения:

1. синтаксис всех изменённых Lua-файлов;
2. загрузка плагина без Lua-ошибок;
3. повторная загрузка после сохранения данных;
4. основной пользовательский сценарий, затронутый изменением;
5. отсутствие регрессии сопоставления текущей цели;
6. корректность ссылок в Markdown.

Для UI, событий цели и миграций используйте полный
[сценарий ручной проверки](manual-test.md). Ограничения API и принятое решение
по сопоставлению цели описаны в [результатах прототипа](prototype-test.md).

## Ветки и релизы

- `staging` содержит изменения для разработки и проверки;
- `main` содержит стабильное состояние;
- тег `vX.Y.Z` должен указывать на `main` и совпадать с `<Version>` манифеста.

GitHub Actions собирает установочный ZIP и SHA-256 после отправки тега.
Пошаговый процесс описан в [инструкции по выпуску](releasing.md).

## Документация

Изменение поведения считается завершённым, когда одновременно обновлены:

- README, если меняется позиционирование или установка;
- руководство пользователя, если меняется интерфейс или команда;
- это руководство, если меняется архитектура или процесс;
- roadmap, если функция добавлена, перенесена или отменена;
- ручной сценарий для нового критичного поведения.

Внутренние решения и черновые декомпозиции не должны становиться частью
коммита или публичных ссылок.
