# ТЗ: Enemy Highlight — плагин для The Lord of the Rings Online

## 1. Назначение

`Enemy Highlight` — плагин для ручного ведения списка знакомых игроков и
отображения личного отношения к текущей выбранной цели.

Пользователь сам присваивает игрокам один из трёх статусов:

- `Friend` — друг, зелёный индикатор;
- `Neutral` — нейтральное отношение, жёлтый или оранжевый индикатор;
- `Enemy` — враг, красный индикатор.

Когда пользователь выбирает в игре персонажа, уже добавленного в список,
плагин показывает рядом с именем текущей цели цветной индикатор её статуса.

Главная цель плагина — помочь пользователю запоминать людей, с которыми он
раньше взаимодействовал, независимо от того, играет пользователь за Свободные
народы или за Игрока-монстра.

Язык пользовательского интерфейса: английский.

## 3. Термины

- **Текущая цель** — сущность, которую пользователь в данный момент выбрал в
  игровом интерфейсе.
- **Известный игрок** — имя персонажа, которое сохранено в базе плагина с одним
  из трёх статусов.
- **Неизвестный игрок** — имя персонажа, отсутствующее в базе плагина.
- **Индикатор** — небольшой цветной визуальный элемент, по умолчанию точка,
  обозначающий сохранённый статус текущей цели.
- **Сторона** — Свободные народы (`Free People`) или Игроки-монстры
  (`Monster Player`). Сторона персонажа не заменяет назначенный пользователем
  статус.

## 4. Основные пользовательские сценарии

### 4.1. Добавление игрока

1. Пользователь открывает основное окно плагина.
2. Вводит имя персонажа.
3. Выбирает статус `Friend`, `Neutral` или `Enemy`.
4. Сохраняет запись.
5. Запись появляется в соответствующем списке и сохраняется между сеансами
   игры.

Пример: пользователь встретил персонажа, который ему навредил, вводит его имя,
выбирает `Enemy` и сохраняет запись.

### 4.2. Распознавание выбранной цели

1. Пользователь выбирает персонажа в игре.
2. Плагин получает имя текущей цели.
3. Плагин ищет это имя в сохранённой базе.
4. Если запись найдена, плагин показывает индикатор соответствующего цвета.
5. При смене или снятии цели индикатор сразу обновляется либо скрывается.

### 4.3. Изменение статуса

1. Пользователь находит существующую запись в окне плагина.
2. Меняет её статус.
3. Запись перемещается в соответствующий список.
4. Если изменённый игрок является текущей целью, индикатор обновляется сразу.

### 4.4. Удаление игрока

1. Пользователь находит запись.
2. Удаляет её.
3. Запись исчезает из базы.
4. Если удалённый игрок является текущей целью, индикатор скрывается сразу.

## 5. Функциональные требования MVP

### 5.1. Работа со списком игроков

Плагин должен:

1. Позволять вручную добавить имя и назначить ему статус `Friend`, `Neutral`
   или `Enemy`.
2. Показывать сохранённые записи, разделённые по статусам. Конкретный вид — три
   колонки либо три вкладки — должен быть определён до реализации.
3. Позволять изменить статус существующей записи.
4. Позволять удалить запись.
5. Не допускать одновременного нахождения одного имени в нескольких статусах.
   Повторное сохранение имени должно обновлять существующую запись.
6. Игнорировать пробелы в начале и конце введённого имени.
7. Сопоставлять имена без учёта регистра, сохраняя исходное написание для
   отображения.
8. Не создавать пустые записи.
9. Показывать понятное английское сообщение, если введённое имя некорректно.

### 5.2. Отслеживание цели

Плагин должен:

1. Отслеживать смену текущей цели локального персонажа.
2. Сразу сохранять нужные данные цели в обычные Lua-значения, поскольку объект
   цели может стать недоступен после смены цели или выхода из радиуса.
3. Получать как минимум имя цели.
4. Проверять тип цели, если API предоставляет надёжный способ отличить игрока
   от NPC и других сущностей.
5. Не показывать индикатор для снятой цели.
6. Не показывать устаревший индикатор после быстрой смены нескольких целей.
7. Корректно обрабатывать `nil`, недоступный объект и ошибки
   недокументированных методов API.

Предполагаемый механизм — `LocalPlayer:GetTarget()` и событие
`LocalPlayer.TargetChanged`. Эти части API считаются недокументированными,
поэтому до разработки полного интерфейса необходимо сделать минимальный
прототип и проверить их в актуальном обычном клиенте LOTRO.

### 5.3. Индикатор статуса

Плагин должен отображать небольшой индикатор:

- зелёный для `Friend`;
- жёлтый или оранжевый для `Neutral`;
- красный для `Enemy`.

Базовая форма индикатора — точка. Она не должна перехватывать клики по игровому
интерфейсу и не должна закрывать имя цели.

LOTRO Lua API, вероятнее всего, не позволяет изменять встроенную строку имени
цели. Поэтому технически безопасный вариант — отдельное прозрачное окно с
индикатором, которое пользователь вручную располагает рядом со штатным окном
цели. Это решение требует подтверждения в разделе 15.

Индикатор должен:

1. Появляться только при наличии применимого статуса.
2. Менять цвет сразу после изменения статуса текущей цели.
3. Скрыться после снятия цели, удаления записи или выбора неподдерживаемой цели.
4. Иметь режим перемещения для первоначальной настройки позиции.
5. Сохранять позицию между сеансами.
6. В обычном режиме быть заблокированным от случайного перемещения.

### 5.4. Стороны PvMP

Плагин должен корректно загружаться и работать как за персонажей Свободных
народов, так и за Игроков-монстров.

Для определения стороны локального персонажа можно изучить использование
`LocalPlayer:GetAlignment()` и `Turbine.Gameplay.Alignment.MonsterPlayer` в
`PvMP_Plus`.

Назначенный пользователем статус является личной оценкой и не должен
автоматически определяться только стороной персонажа. Требование о раздельных
или общих списках для двух сторон пока не определено и вынесено в раздел 15.

## 6. Основное окно

Интерфейс окна должен быть на английском языке и содержать как минимум:

- заголовок `Enemy Highlight`;
- поле `Player name`;
- выбор статуса `Friend / Neutral / Enemy`;
- кнопку добавления или сохранения записи;
- списки сохранённых игроков;
- действие изменения статуса;
- действие удаления записи;
- кнопку закрытия окна.

Требования к поведению окна:

1. Окно можно перемещать.
2. Его последняя позиция сохраняется.
3. Закрытие окна не выгружает плагин и не отключает индикатор.
4. Повторное открытие не создаёт дубликат окна.
5. Длинные списки должны прокручиваться.
6. Для потенциально необратимых действий вроде очистки всей базы необходимо
   подтверждение. Обычное удаление одной записи может выполняться без
   подтверждения.
7. Окно должно оставаться в пределах экрана после изменения разрешения, если
   это можно надёжно реализовать средствами API.

Точный размер, оформление, а также выбор между колонками и вкладками должны
быть согласованы до реализации.

## 7. Хранение данных

Для хранения использовать `Turbine.PluginData.Load` и
`Turbine.PluginData.Save`.

Данные должны включать:

- версию формата данных;
- отображаемое имя игрока;
- нормализованный ключ имени для поиска;
- статус игрока;
- настройки и позицию окон.

Требования:

1. Данные загружаются при запуске плагина.
2. Изменения записей и настроек сохраняются после совершения действия, а не
   только при выгрузке плагина.
3. Отсутствующий файл данных считается первым запуском и не вызывает ошибку.
4. Повреждённые или частично устаревшие данные не должны ломать загрузку всего
   плагина; ошибка выводится в чат, а доступные записи по возможности
   сохраняются.
5. Формат должен предусматривать последующие миграции через поле версии.
6. Область хранения (`Account`, `Server` или `Character`) должна быть выбрана
   после ответа на вопросы раздела 15.

## 8. Команды чата

Предлагаемый префикс команд: `/eh`.

Минимальный набор:

- `/eh` или `/eh toggle` — открыть или скрыть основное окно;
- `/eh show` — открыть основное окно;
- `/eh hide` — скрыть основное окно;
- `/eh move` — включить режим перемещения индикатора;
- `/eh lock` — зафиксировать индикатор;
- `/eh help` — показать список команд.

Неизвестная команда не должна вызывать Lua-ошибку: плагин должен показать
краткую английскую справку.

Названия команд являются предложением и требуют подтверждения.

## 9. Особые случаи

- Если цель отсутствует, индикатор скрыт.
- Если имя цели отсутствует в базе, поведение определяется ответом на вопрос о
  неизвестных игроках в разделе 15.
- Если выбрана NPC, питомец, предмет или другая неподдерживаемая сущность,
  индикатор скрыт.
- Если цель быстро меняется, показывается статус только последней цели.
- Если одно и то же имя добавлено в другом регистре, обновляется существующая
  запись.
- Если имя переводится из одного статуса в другой, старая запись удаляется из
  прежнего списка.
- Если API временно вернул `nil`, плагин скрывает индикатор и не завершает
  работу с ошибкой.
- Перезагрузка плагина не должна терять сохранённый список и позиции окон.
- Ошибка сохранения должна быть выведена в чат и не должна уничтожать текущие
  данные в памяти.

## 10. Что не входит в MVP

Без отдельного согласования плагин не должен:

- автоматически назначать статус по стороне, расе, классу, племени или
  содружеству персонажа;
- автоматически собирать имена всех игроков вокруг пользователя;
- автоматически выбирать игровые цели;
- изменять поведение боя или отправлять команды без действия пользователя;
- читать или изменять файлы других плагинов;
- синхронизировать базу через интернет;
- добавлять заметки, историю встреч, дату последней встречи, импорт и экспорт;
- изменять штатные элементы интерфейса способом, не поддерживаемым API.

## 11. Предлагаемая структура проекта

Окончательная структура может быть скорректирована после изучения примеров,
но логика должна быть разделена как минимум на следующие части:

- точка входа и загрузка модулей;
- модель и хранилище отношений;
- отслеживание текущей цели;
- основной интерфейс управления списком;
- отдельный индикатор статуса;
- команды чата;
- английские строки интерфейса;
- файл манифеста `.plugin`;
- `README.md`.

Namespace и каталог плагина: `EnemyHighlight`, если в ходе проверки не будет
найден конфликт с требованиями LOTRO.

## 12. Технические требования

- Не изменять плагины-примеры.
- Использовать понятные имена и не создавать лишние глобальные переменные.
- Разделить интерфейс, данные, сохранение и обработку игровых событий.
- Не назначать обработчики событий способом, который стирает обработчики
  других плагинов. Использовать совместимый механизм добавления и снятия
  callback-функций.
- Снимать зарегистрированные обработчики при выгрузке плагина, если API и
  жизненный цикл это позволяют.
- Не выполнять постоянный опрос каждый кадр, если смену цели можно надёжно
  обработать событием.
- Защитить обращения к недокументированным методам проверками и/или `pcall`.
- Не добавлять зависимости без необходимости.
- Не оставлять заглушки в обязательной функциональности.
- Пользовательские сообщения и подписи должны быть на английском языке.

## 13. Порядок реализации

1. Изучить указанные локальные плагины и доступную документацию Turbine API.
2. Создать минимальный технический прототип: получить имя выбранной цели,
   обработать смену и снятие цели, проверить Свободные народы и
   Игрока-монстра.
3. Описать фактически доступные свойства цели и ограничения API.
4. Если прототип не работает в актуальном клиенте, остановить полную
   реализацию, сообщить о блокере и предложить ближайший допустимый вариант.
5. После подтверждения прототипа реализовать хранилище и операции со списком.
6. Реализовать индикатор.
7. Реализовать основное окно и команды.
8. Проверить загрузку, сохранение, обработку ошибок и крайние случаи.
9. Подготовить документацию по установке и ручной проверке в игре.

## 14. Критерии готовности

MVP считается готовым, если:

1. Плагин обнаруживается менеджером плагинов LOTRO и загружается без Lua-ошибок.
2. Пользователь может добавить, изменить и удалить запись.
3. Одно имя не может одновременно иметь несколько статусов.
4. Данные не теряются после перезагрузки плагина и повторного входа в игру.
5. При выборе известного игрока показывается индикатор правильного цвета.
6. При смене статуса текущей цели цвет меняется сразу.
7. При снятии цели, выборе неподдерживаемой сущности или удалении текущей записи
   индикатор скрывается.
8. Смена цели не оставляет индикатор от предыдущего персонажа.
9. Плагин работает за Свободные народы и за Игрока-монстра либо документирует
   подтверждённое ограничение API.
10. Основное окно и индикатор сохраняют положение.
11. Все заявленные команды чата работают и не вызывают ошибок при неверном
    вводе.
12. Файлы плагинов-примеров не изменены.
13. Создан `README.md` с установкой, загрузкой, командами, использованием,
    ограничениями API и сценарием ручной проверки.

Проверку поведения цели и отображения необходимо выполнить вручную внутри
обычного клиента LOTRO. Статический анализ Lua не заменяет эту проверку.

## 15. Вопросы, требующие ответа до полной реализации

1. Допустим ли отдельный перемещаемый индикатор рядом со штатным именем цели,
   если встроить точку непосредственно в стандартный интерфейс LOTRO нельзя?
   - Да, допустим.
2. Что показывать для игрока, которого ещё нет в базе: ничего или нейтральный
   индикатор? Является ли `Neutral` явно сохранённым статусом?
   - Ничего не показывать
3. Должна ли база быть общей для всех персонажей аккаунта, общей только внутри
   одного сервера или отдельной для каждого персонажа?
   - Внутри одного сервера
4. Должны ли персонажи Свободных народов и Игроки-монстры видеть одну общую базу
   отношений или отдельные базы?
   - Одна общая база
5. Как должен выглядеть список: три одновременно видимые колонки или три
   вкладки?
   - Три вкладки
6. Какой точный цвет выбрать для `Neutral`: жёлтый или оранжевый?
   - Оранжевый
7. Нужна ли кнопка, которая подставляет имя текущей цели в поле добавления, или
   имя всегда вводится вручную?
   - Если есть возможность добавить кнопку, то можно добавить
8. Подходят ли предложенные команды `/eh`?
   - Да, но давай добавим еще и команду что-то типа "/eh add <NICKNAME>"
9. Нужно ли хранить только имя или также необязательную текстовую заметку о
   персонаже? Заметки сейчас не включены в MVP.
   - Давай сделаем с заметками, то ест в окне, со списком, можно будет проваливаться в карточку отдельного игрока

## 16. Инструкция Codex для итоговой реализации

Перед началом реализации прочитать этот документ полностью и получить ответы

поведение.

В ходе работы:

1. Найти и соблюдать локальные инструкции `AGENTS.md`, если они существуют.
2. Сначала проверить техническую реализуемость отслеживания цели в игре.
3. Не изменять примеры плагинов.
